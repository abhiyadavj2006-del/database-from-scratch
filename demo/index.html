minidb — a database from scratch

A minimal but real persistent database, written in Python with only the standard library. No server, no dependencies, no accounts, no paid services.

It is not a hosted database. This page is a static demo of what the code does — the database itself runs on your own machine from the terminal. See How to run it below.

What it does

  • Tables — CREATE TABLE users (id INT, name TEXT, age INT);
  • INSERT / SELECT — with WHERE filters (=, !=, <, >, <=, >=, AND), plus UPDATE and DELETE.
  • A real B-tree index — CREATE INDEX builds a B-tree (minimum degree 3) over a column. Equality and range lookups use it; other queries fall back to a full scan. EXPLAIN shows which plan was chosen.
  • Persistence to disk — a database is a directory (demo.db/) holding meta.json and one <table>.json file per table. Writes are atomic (write to .tmp, then rename), so closing and reopening the database keeps your rows. Indexes are rebuilt from the table files on open.
  • A CLI / REPL — cli.py, with .help, .tables, .exit, script mode (--file demo.sql) and piped input.

How the B-tree index works

Each indexed column gets its own B-tree. Keys are the column values (sorted inside every node); each key maps to a bucket of row ids, so duplicate values (e.g. two users aged 30) share one key. Every leaf is at the same depth, so the tree stays balanced and search / insert cost O(log n).

With minimum degree t = 3, a node holds at most 5 keys and 6 children. The height bound is logt((n+1)/2) + 1 — for 200 rows that is about 5, and the test suite verifies a 200-row tree has height 5 and that every key is still findable. Sequential inserts leave nodes at minimum occupancy (2 keys), so the height is at the bound rather than below it; a larger t would be the next tuning step for disk-sized pages.

When a node fills up it splits: the median key moves up to the parent, the node becomes two half-full nodes, and if the root splits the tree grows one level taller. That is the whole trick — splits, not rebalancing passes, keep the tree balanced.

How to run it

Requirements: Python 3.10+ only. No packages to install, no environment variables, no network.

git clone <your-repo-url> database-from-scratch
cd database-from-scratch
python3 test_db.py            # 31 automated checks
python3 cli.py demo.db --file demo.sql   # run the demo
python3 cli.py demo.db        # interactive REPL; try:
#   SELECT * FROM users WHERE age = 30;
#   EXPLAIN SELECT * FROM users WHERE age = 30;

What it does not do (yet)

  • No JOINs, no ORDER BY / LIMIT / GROUP BY, no NULLs, no primary-key / uniqueness enforcement.
  • No transactions, WAL, or crash recovery beyond atomic file replacement; no concurrency control (single process, single writer).
  • No persistence of the index itself — it is rebuilt on open (fast for small tables, a cost at scale).
  • Whole-table JSON files are rewritten on every write, so it is not suited to large tables. A page-based storage file is the natural next step.
