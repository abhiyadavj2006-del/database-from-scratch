minidb — a database from scratch

A minimal but real persistent database, written in Python with only the standard library. No server framework, no dependencies, no accounts, no paid services. It follows the architecture of “Writing My Own Database From Scratch” by Antonio Sarosi (source: antoniosarosi/mkdb): one file of 4 KiB pages, B-trees on slotted pages, a clock page cache, journal transactions, and a TCP server.

It is not a hosted database. This page is a static demo of what the code does — the database itself runs on your own machine from the terminal. See How to run it below.

What it does

  • Tables — CREATE TABLE users (id INT PRIMARY KEY, name TEXT NOT NULL, age INT, email TEXT UNIQUE);
  • INSERT / SELECT / UPDATE / DELETE — with WHERE filters (=, !=, <, >, <=, >=, AND, OR, IS NULL), multi-row INSERT, and ORDER BY … LIMIT … OFFSET … (big sorts spill to temp files and merge K-way, like the video's external merge sort).
  • Constraints — PRIMARY KEY (the table itself is a B-tree keyed by it, like SQLite's index-organized tables), NOT NULL, UNIQUE, and NULL values.
  • Real on-disk B-tree indexes — CREATE INDEX builds a B-tree over a column, keyed by (value, primary key). Equality and range lookups use it; other queries fall back to a full scan. EXPLAIN prints the whole query plan tree (Limit → Project → Sort → Filter → IndexScan).
  • Transactions — BEGIN / COMMIT / ROLLBACK, plus one implicit transaction per statement. Before a page is first modified, its original bytes go to a journal file; commit deletes the journal, rollback restores it, and a journal found at startup is rolled back automatically — crash recovery.
  • Persistence to disk — a database is a directory holding one file, data.db: a sequence of 4 KiB pages. Page 0 is the header, the schema lives in its own B-tree, each table is a B-tree, and rows bigger than a quarter of a page spill to overflow pages. A clock cache keeps hot pages in memory.
  • A CLI / REPL — cli.py, with .help, .tables, .exit, script mode (--file demo.sql) and piped input — and a TCP server (server.py, length-prefixed protocol, one writer at a time) with a matching client (server.py --client).

How storage works

One file, fixed-size pages. data.db is a sequence of 4 KiB pages; page number × 4096 is the file offset. Page 0 is the header (magic, page count, schema-tree root, free-page list). The schema itself is a B-tree (the minidb_meta catalog), and every table and index is a B-tree whose nodes are pages.

Slotted pages. A B-tree node page holds a slot directory that grows right from the page start and cell bytes that grow left from the page end. Reordering cells means shifting 4-byte slot entries, not moving the variable-length row bytes — and a binary search over the fixed-size slots finds any key.

Index-organized tables. The table is a B-tree sorted by primary key, so each cell is a full row. A secondary index stores (value, primary key); looking a row up by email costs two B-tree searches (index, then table) instead of a fragile physical row address.

Overflow pages. A row bigger than a quarter of a page keeps its first chunk in the cell; the cell's last 4 bytes point at an overflow page, whose header points at the next one — a linked list that is reassembled on read.

Clock cache + journal. Hot pages sit in a clock (second-chance) cache with reference and dirty bits; the hand evicts the first frame with ref = 0, writing it back first if dirty. Before a page is first modified in a transaction, its original bytes are appended to the journal file; commit flushes and deletes the journal, rollback copies the originals back — and a journal found at startup means the last transaction crashed, so it is rolled back automatically.

SQL pipeline. Text → tokenizer → parser (AST) → analyzer (table/column/type checks) → planner (index vs full scan) → iterator plan (SeqScan/IndexScan → Filter → Sort → Project → Limit), where each node yields one tuple at a time. Sort sorts in memory while the result fits, and spills sorted runs to temp files for a K-way merge when it does not.

How to run it

Requirements: Python 3.10+ only. No packages to install, no environment variables, no network.

git clone <your-repo-url> database-from-scratch
cd database-from-scratch
python3 test_db.py            # 31 baseline checks
python3 test_advanced.py      # 59 advanced checks (pager, transactions, sort, server)
python3 cli.py demo.db --file demo.sql   # run the demo
python3 cli.py demo.db        # interactive REPL; try:
#   SELECT * FROM users WHERE age = 30;
#   BEGIN; UPDATE users SET age = 31 WHERE id = 1; ROLLBACK;
python3 server.py demo.db 8000   # TCP server (another terminal:)
python3 server.py --client 127.0.0.1 8000

What it does not do (yet)

  • No JOINs, no GROUP BY / aggregates, no subqueries. One table per SELECT.
  • No MVCC or concurrent writers — one transaction at a time, one writer lock (same as the video's toy engine; production systems use WAL + MVCC instead of a journal).
  • No B*-tree redistribution: nodes split at the median (classic CLRS B-tree) instead of mkdb's balance-on-demand. Deletes are tombstones, not full B-tree removal with merging — space is reclaimed only when a whole tree is dropped.
  • No CHECK / DEFAULT / foreign keys, no ALTER TABLE, no DROP INDEX.
  • Rows are JSON bytes inside cells (simple and robust), not mkdb's packed binary tuple format; keys compare after decoding rather than by raw memcmp.
